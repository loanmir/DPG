# 1a — A folded edge keeps the weight of the edge it replaces

**Problem:** report #1, "Edge weights are summed when chains are folded". A chain
`A -43-> B -43-> C -43-> Class` becomes `A∧B∧C -129-> Class` although the same 43 traces flow
through it. CONJUNCTION/DEDUP inflate the weight into the class nodes up to 4.46×.
**Approach:** when a node absorbs its successor, the successor's outgoing edges move to the
absorbing node **with their own weight**. Nothing is added.
**Depends on:** 0a. **Followed by:** 1b (clones), which together with this plan brings every
view back to 1.00×.

## Why this is the right weight

An edge weight in a DPG counts trace transitions: `w(x → y)` = number of (row, tree) traces in
which test `y` immediately follows test `x`. After `u` absorbs `v` along the private edge `u → v`,
the merged node's edge to `d` stands for "the traces that passed `u`, then `v`, then went to `d`".
When `v`'s only parent is `u`, those are exactly the `w(v → d)` traces that left `v` towards `d`
(ignoring traces that *start* at `v`, see #11). The sum `w(v → d) + w(u → v)` counts every
trace twice or more. The minimum along the chain would also be defensible, but it is wrong as
soon as the tail branches (each branch carries only part of the flow), so use `w(v → d)`.

## Changes

There are four places. In each, keep the existing `edges.get(key, 0.0) + ...` accumulation for
the case where the key already exists (two different flows reaching the same `d` *should* add up),
but drop the absorbed edge's weight from the sum.

1. `categorical/cat_grouping.py`, `_apply_grouping`:
   * delete the `internal_sum = sum(...)` computation;
   * in the loop over `succ.get(tail, [])`, change
     `grouped_weights.get(new_key, 0.0) + original + internal_sum` to
     `grouped_weights.get(new_key, 0.0) + original`.
   * Docstring of `_apply_grouping`: replace the paragraph "The run's merged outgoing edge(s) carry
     every weight the run absorbs: ..." with: the run's outgoing edges keep the weight of the tail's
     outgoing edges, because the same traces flow along the whole private chain.
   * Module docstring: the example `(weight 56 + 212 = 268)` becomes `(weight 212)`, and adjust
     the sentence above it.
   * `_build_grouped_structure` docstring: "(which already sums the absorbed weights onto the
     leader's outgoing edge)" → "(the leader's outgoing edges carry the tail's weights)".
   * `_build_dot` comment "collapsed-segment weights have been summed" → update accordingly.
2. `categorical/cat_grouping_split.py`, inner function `_fold_forward`:
   `edges[key] = edges.get(key, 0.0) + w + w_uv` → `edges[key] = edges.get(key, 0.0) + w`.
   The parameter `w_uv` becomes unused: remove it from the signature and from the call in
   `_split_then_merge`. Update the docstring ("with ``w_uv`` folded into each" → "with their own
   weight") and the module docstring sentence "the weight folds forward onto whatever comes after
   ``v``" → "``v``'s outgoing edges move onto ``u`` unchanged".
3. `categorical/cat_grouping_split_conjunction.py`, inner function `_fold_forward`: same change
   as 2 (remove `w_uv` from signature, docstring and call). Module docstring: "and the
   weight-folding rules" stays in the list of things identical to the split script, which is
   still true.
4. `categorical/cat_duplicate_split_peer.py`, `_deduplicate_labels`, branch `if not new_child:`
   (node `v` dropped): `weights[key] = weights.get(key, 0.0) + w + w_uv` →
   `weights[key] = weights.get(key, 0.0) + w`. Here `(u, d)` may already exist (u keeps other
   children); then adding `w` is correct, because the direct `u → d` traces and the
   `u → v → d` traces are different traces. Remove the now unused `w_uv = weights[(u, v)]` line.
   Update the module docstring sentence "its single incoming edge is rewired onto its outgoing
   edges with the original edge weights summed (matching the rest of the project's split-then-merge
   convention)" → "... onto its outgoing edges, which keep their own weights" and the inline
   comment "with the original edge weights summed. Matches the project's split-then-merge fold
   convention."

Do not touch `_clone_node` (that is 1b) or any merge criterion.

## Tests — `tests/categorical/test_weights.py`

Use `make_structure`, `view_edges`, `view_labels` from `tests/categorical/conftest.py`.

1. **GROUPED chain.** Nodes `a: "X_p <= 0.5"`, `b: "X_q <= 0.5"`, `c: "X_r <= 0.5"`, `k: "Class 1"`;
   edges `a→b 43`, `b→c 43`, `c→k 43`. Run `cat_grouping._build_label_map` then
   `_apply_grouping`. Expect one merged node `X NOT IN {p, q, r}` and the edge `(a, k)` with weight 43.
2. **SPLIT chain.** Same input through `cat_grouping_split._split_then_merge(structure, label_map)`.
   Expect edges `{("a", "k"): 43.0}`.
3. **CONJUNCTION chain across features.** `a: "X_p <= 0.5"`, `b: "Y_s > 0.5"`, `k: "Class 1"`,
   `a→b 10`, `b→k 10` through `cat_grouping_split_conjunction._split_then_merge`. Expect
   `{("a", "k"): 10.0}` and label `X NOT IN {p} AND Y IN {s}`.
4. **Branching tail.** `a: "X_p <= 0.5"`, `b: "X_q <= 0.5"`, `k1: "Class 0"`, `k2: "Class 1"`,
   `a→b 30`, `b→k1 20`, `b→k2 10`, through all three grouping functions: the merged node has
   edges to `k1` = 20 and `k2` = 10.
5. **DEDUP drop.** Conjunction-shaped input (labels already in `IN`/`NOT IN` form, since dedup reads
   the CONJUNCTION JSON): `u: "X IN {a}"`, `v: "X IN {a} AND X IN {a}"`, `w: "Y NOT IN {b}"`,
   `k: "Class 1"`, edges `u→v 10`, `v→w 7`, `w→k 7`. `cat_duplicate_split_peer._deduplicate_labels`
   drops `v` and the new edge `(u, w)` must weigh 7.
6. **DEDUP drop onto an existing edge.** As 5, plus a direct edge `u→w 3`: after the drop,
   `(u, w)` = 10 (3 direct + 7 via `v`).
