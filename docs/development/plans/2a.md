# 2a — Detect categorical columns the way `pd.get_dummies` does

**Problem:** report #2. `dpg_equivalence.load_categorical_domains` keeps a column only if
`df[col].dtype == object` (or a category dtype). Under pandas 3 text columns have the `str` dtype,
the function returns no domains, and `explanation_agreement` / `explanation_overlap` drop to
0.43–0.59. The pinned environment (pandas 2.2.3) hides the bug. It comes back as soon as someone
installs pandas 3.
**Approach:** a column is categorical exactly when `pd.get_dummies` would one-hot encode it. Put
that rule in a new small module `categorical/onehot.py` (7a extends the same module) and use it
in `load_categorical_domains`.
**Depends on:** 0a.

## Changes

1. New file `categorical/onehot.py`:

   ```python
   """One-hot encoding facts shared by the categorical pipeline.

   Which columns are categorical is decided exactly the way the training
   pipeline's ``pd.get_dummies(features, drop_first=False)`` decides it, so
   the answer does not depend on the pandas version's text dtype (``object``
   under pandas 2, ``str`` under pandas 3).
   """
   from __future__ import annotations

   from typing import List

   import pandas as pd


   def categorical_columns(df: pd.DataFrame) -> List[str]:
       """Columns of ``df`` that ``pd.get_dummies`` one-hot encodes, in column order."""
       encoded = set(pd.get_dummies(df.head(1), drop_first=False).columns)
       return [c for c in df.columns if c not in encoded]
   ```

   `df.head(1)` is enough to decide *which* columns get encoded (it depends on the dtype only), and
   avoids encoding a 381k-row dataset just to read column names. Check this claim in a test (see
   below), including a column that is all-NaN in the first row.
   Caveat to verify: a numeric column whose name equals an encoded dummy name would hide the
   difference. Assert in the function that no original column name is also produced as a dummy name
   by another column; raise `ValueError` if it is.

2. `categorical/dpg_equivalence.py`, `load_categorical_domains`: replace the dtype test

   ```python
   for col in df.columns:
       if not (df[col].dtype == object or str(df[col].dtype).startswith("category")):
           continue
   ```

   with a loop over `categorical_columns(df)`. `dpg_equivalence` is always imported as
   `categorical.dpg_equivalence` (by `run_all_metrics.py`), so import the helper relatively at the
   top of the module: `from .onehot import categorical_columns`. Keep the `0 < len(values) <= 1024`
   filter and update the docstring ("every string-typed column" → "every column that
   `pd.get_dummies` one-hot encodes").

   Note: `df` here still contains the target column (last column). Today a string target gets a
   domain too. Keep that behaviour, so the result under pandas 2.2.3 is identical.

3. No other file in `categorical/`, `dpg/` or `metrics/` uses `dtype == object` (checked with
   `grep -rn "== object" categorical dpg metrics`). Re-run that grep; if a new hit appeared, apply
   the same helper there.

## Tests — `tests/categorical/test_onehot.py`

1. `categorical_columns` on a frame with an object column, a `pd.StringDtype()` column (this is
   what pandas 3 produces for text), a category column, an int column, a float column and a bool
   column returns exactly the object, string and category columns. (`pd.get_dummies` does not
   encode bool columns; the test pins that.)
2. A text column whose first value is `NaN` is still detected.
3. `load_categorical_domains` on a temporary CSV (write with `tmp_path`) returns the expected
   domains, and returns the **same** domains when the frame is read and then converted with
   `df.convert_dtypes()` (simulating string dtypes). To do the second part without a CSV, factor the
   body of `load_categorical_domains` after `read_csv` into a helper
   `_domains_from_frame(df) -> Dict[str, frozenset]` and test that.
